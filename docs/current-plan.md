# AITrade 当前方案

> 文档状态：**当前唯一产品方案**。本文同时记录已经落地的能力、当前边界和下一阶段实施计划。文中的“已落地”表示代码和测试已经存在；“规划”表示尚未实现，不能当作现有功能对外宣传。

## 1. 产品定位

产品定位是“个人跨境电商工作流”，稳定后再升级为小团队工作流。目标不是再增加一组报表页面，而是让每个商品都回答四个问题：

1. 现在处在哪个阶段？
2. 当前健康吗？
3. 下一步该做什么？
4. 上一次判断和实际结果差多少？

系统采用“生命周期状态 + 经营域状态”双轴模型。选品、供应商与样品、内容上架可以顺序推进；发布后的广告、库存、客服和财务并行运行，不能强行设计成单线程状态机。

```text
选品验证
→ 供应商与样品
→ 内容上架
→ 广告测试 / 库存物流 / 客服评价（并行）
→ 财务复盘
→ 反哺选品、供应商评分和成本模型
```

### 2.2 部分落地

- 供应商助手只生成内部草稿，支持复制和标记已审阅，**不发送、不联系供应商、不写 `sent_at`**。
- 内容工作台可以手工维护商品事实、图片和 Listing，但**没有 AI Listing 操作员**。
- 平台能力只有本机预检和发布准备队列，**没有真实 dry-run、官方写 Adapter、平台发布或外部回执**。
- 成本模型只有预测利润，**没有实际结算和实际 SKU 利润**。
- 选品阶段有竞品评论分析，但**没有发布后的客服、退货和评价闭环**。

## 3. 产品原则

- 以 SKU 为经营主对象，不以页面或报表为主对象。
- 预测数据与实际数据分开保存，禁止混用。
- 最终财务数字由确定性计算器产生，AI 只做解释、归类和草稿。
- 每个异常必须绑定指标、原始数据和计算口径。
- 每个行动卡片必须有负责人、优先级、截止时间和审批记录。
- 外部改价、广告预算、补货、清仓、退款和发布始终需要人工批准。
- 单编排器 + 专用 Skill；不引入多个 Agent 自由协商。
- 先接 CSV 和人工导出，再逐步接官方 API；不能因为接入慢而阻塞业务闭环。

## 4. 双轴状态模型

### 4.1 生命周期阶段

```text
validating
→ sampling
→ content_ready
→ listing_ready
→ published
→ operating
→ profit_review
→ scaling | holding | clearing
→ archived
```

阶段含义：

- `validating`：机会假设、竞品、差评、供应商和报价验证中。
- `sampling`：供应商已定标，样品和合规文件处理中。
- `content_ready`：样品通过，商品定义、图片和 Listing 可以制作。
- `listing_ready`：内容已确认，发布预检通过。
- `published`：已有真实平台发布回执或人工发布记录。
- `operating`：广告、库存、客服和财务数据持续进入。
- `profit_review`：达到复盘周期，正在核对实际利润。
- `scaling`：实际利润和库存周转健康，可以扩大。
- `holding`：暂不扩大，继续观察或优化。
- `clearing`：准备清仓或退出。
- `archived`：停止经营，保留历史数据。

状态变化必须通过受控 transition 完成，并写入 `sku_stage_events`。不能仅通过更新一个字符串字段改变阶段。

### 4.2 经营域状态

发布后，以下域并行运行：

| 经营域 | 状态 |
|---|---|
| 广告 | `not_started / testing / healthy / attention / stopped` |
| 库存物流 | `healthy / low_stock / stockout_risk / overstock / blocked` |
| 客服评价 | `healthy / needs_reply / quality_issue / claim_risk / blocked` |
| 财务 | `pending_data / reconciling / healthy / margin_risk / loss` |

首页和商品 360 页面分别展示生命周期阶段与四个经营域状态，避免把“正在补货”和“广告测试中”错误地合并成一个状态。

## 5. 八阶段进入与退出条件

| 阶段 | 进入条件 | 必须产出 | 退出条件 |
|---|---|---|---|
| 1. 选品验证 | 有明确市场、平台和品类假设 | 证据包、成本模型、确定性门禁结论 | GO，或明确终止/继续补证据 |
| 2. 供应商与样品 | GO 或人工批准的候选商品 | 定标供应商、样品单、质检报告、合规文件 | 样品通过，资料齐全，供应商可采购 |
| 3. 内容上架 | 样品通过且商品事实已确认 | 商品定义、图片、Listing 版本、预检和发布记录 | 已发布或有可追溯的人工发布回执 |
| 4. 广告测试 | 已发布，有售价、毛利和预算上限 | 单变量实验、每日花费、转化和止损记录 | 达到样本量，输出继续/调整/停止结论 |
| 5. 库存物流 | 已发布，有库存或在途数据 | 可用库存、在途、交期、库存天数和补货建议 | 库存健康，或补货/清仓行动已批准 |
| 6. 客服评价 | 已有订单、评价或售后消息 | 问题分类、退货原因、回复草稿、缺陷标签 | SLA 达标，重复问题进入产品改进池 |
| 7. 财务复盘 | 有结算、广告、采购、退款和物流费用 | 实际 SKU 利润、现金流、预测差异 | 差异有解释，成本或售价动作已决策 |
| 8. 反哺选品 | 至少有一个完整经营周期 | 供应商评分、品类经验、预测偏差和规则调整 | 更新下一轮选品参数和成本假设 |

## 8. 指标和确定性规则

### 8.1 指标口径

| 指标 | 口径 |
|---|---|
| 实际净销售额 | 成交收入 − 折扣 − 退款 |
| 贡献利润 | 净销售额 − 采购成本 − 平台费 − 履约费 − 广告费 − 退货损失 − 仓储和其他费用 |
| 实际净利率 | 贡献利润 / 净销售额 |
| ACOS | 广告花费 / 广告带来的销售额 |
| TACOS | 广告花费 / 总销售额 |
| 盈亏平衡 ACOS | 广告前贡献毛利 / 广告销售额 |
| 库存天数 | 可用库存 / 最近 28 天日均销量 |
| 入库覆盖缺口 | 库存天数 − 供应商交期 − 安全库存天数 |
| 退货率 | 退货数量 / 发货数量 |
| 预测误差 | (实际利润 − 预测利润) / |预测利润| |

所有公式由 TypeScript 确定性函数实现；模型不得自行计算最终财务数字。

### 8.2 首批异常规则

阈值必须可按市场、平台、品类配置，不能在代码里写死。

| 规则 | 默认观察窗口 | 输出 |
|---|---|---|
| 连续亏损 | 7 天 | `profit_negative` 行动卡 |
| 实际净利率低于目标 | 14 天 | `margin_below_target` |
| ACOS 高于盈亏平衡 ACOS | 最低点击量 + 7 天 | `ad_waste` |
| 库存覆盖小于交期 + 安全天数 | 每日 | `stockout_risk` |
| 库龄超过阈值 | 30/60/90 天 | `overstock` |
| 退货率突增且缺陷集中 | 7 天对比前 28 天 | `quality_issue` |
| 售后消息超过 SLA | 每小时 | `service_sla` |
| 实际利润与预测偏差超过阈值 | 月度 | `forecast_drift` |

同一条规则只生成一个开放行动卡片，使用指纹幂等。重复导入不能重复报警。

## 9. AI Skill 边界

| Skill | AI 负责 | 确定性代码负责 | 人工负责 |
|---|---|---|---|
| 报表映射 | 建议字段映射、解释差异 | Schema、单位、币种、去重和总量校验 | 确认未知字段和映射例外 |
| 样品质检提取 | 从质检文本提取规格和缺陷 | 缺陷分类、阈值、样品状态和证据定位 | 确认样品通过/否决 |
| 广告分析 | 解释搜索词、浪费和实验结论 | ACOS、TACOS、样本量、预算和止损线 | 批准调预算、停投和新建活动 |
| 库存风险 | 解释交期和异常 | 库存天数、补货点、在途和现金占用 | 批准补货、清仓和采购 |
| 客服分诊 | 分类问题、提取缺陷、生成回复草稿 | SLA、风险关键词、责任归属和重复问题检测 | 批准外部回复、退款和索赔 |
| 财务差异 | 解释预测与实际差异 | 利润、费用、退款和现金流计算 | 确认调账和修改成本假设 |
| 反哺分析 | 总结品类和供应商经验 | 样本量、成功率、偏差和评分计算 | 确认更新选品规则 |

AI 输出统一包含：

```json
{
  "summary": "",
  "evidenceRefs": [],
  "affectedEntities": [],
  "recommendedActions": [],
  "confidence": 0,
  "requiresReview": true
}
```

没有证据引用、指标口径或业务规则的结果不得写入业务表。

```text
open
→ reviewing
```

- `evidence_refs`
- `recommended_action`
- `expected_impact`

### 10.3 风险分级

- L0：只读分析和内部草稿，可自动生成。
- L1：内部任务、提醒和整改单，可自动创建但需要负责人确认。
- L2：改价、广告预算、补货、清仓、客服外部回复，必须人工批准。
- L3：采购付款、退款、赔付、法律和合规结论，禁止自动执行。

## 11. 分阶段交付

工期按单人或一到两人小团队估算，真实样本验收时间另计。

### P3.0 生命周期与行动底座

目标：让系统知道每个商品现在在哪里。

交付：

- `sku_stage_events`、`channel_sku_mappings`、`action_cards`
- SKU 360 页面和阶段时间线
- 阶段 transition 审计
- 统一行动卡片状态和负责人

完成定义：

- 100% 活跃商品有当前阶段。
- 每次阶段变化都有原因和审计。
- 首页能显示每个商品的下一步动作。

### P3.1 供应商与样品闭环

交付：

- 样品申请、收样、质检、缺陷和结论
- 认证与合规文件归档
- 样品通过后才能解锁内容制作
- 供应商报价、交期、次品率和响应评分

完成定义：

- 样品状态可追溯。
- 未通过样品或缺合规文件时不能进入内容阶段。
- 供应商评分可由实际报价和质检结果更新。

### P3.2 实际利润与库存

交付：

- 结算、库存、物流费用和退货 CSV
- `actual_results`、`inventory_snapshots`、`forecast_variances`
- 库存天数、补货点和利润差异规则
- 财务与库存行动卡片

完成定义：

- 任意导入指标可以追溯到原始快照。
- 实际利润和预测利润分开展示。
- 库存覆盖不足能生成补货建议，但不自动下单。

### P3.3 广告测试

交付：

- 广告活动、搜索词和每日花费导入
- 单变量实验、预算上限、止损线和样本量
- ACOS、TACOS、盈亏平衡 ACOS
- 继续/调整/停止的行动建议和人工审批

完成定义：

- 每个实验只能改变一个变量。
- 实验结论可追溯到指标快照。
- 不会自动调预算或停投。

### P3.4 客服、评价和退货

交付：

- 售后消息、评价、退货原因和缺陷分类
- 回复草稿、SLA、升级和退款边界
- 重复缺陷进入产品改进池
- 供应商责任和售后评分

完成定义：

- 高危关键词不会自动外发。
- 退货原因可以按 SKU 和供应商聚合。
- 重复质量问题能反哺供应商与选品规则。

### P3.5 反哺与团队协作

交付：

- 预测误差、供应商评分和品类经验
- 选品参数和成本模型的人工确认更新
- Owner / Reviewer / Operator 基础角色
- 任务分派、评论、通知和审核分离

完成定义：

- 每个实际经营结果都能解释对选品参数的影响。
- 高风险动作提交人与审核人可分离。
- 经营经验不会只留在某个人的记忆里。

## 12. 验收指标

### P3.0

- 活跃 SKU 阶段覆盖率 100%。
- 阶段变化审计覆盖率 100%。
- 每个开放异常最多一个行动卡片。

### P3.1

- 样品从申请到结论的状态完整率 100%。
- 样品、合规和供应商资料可从 SKU 360 追溯。

### P3.2

- 结算、库存、退货报表关键字段映射时间小于 10 分钟。
- 实际利润与预测利润可按 SKU、渠道和月份追溯。
- 未知 SKU 映射不能静默写入。

### P3.3

- 广告实验结论可复现。
- 任何预算调整都必须有批准记录和回滚方案。

### P3.4

- 售后消息 SLA 可统计。
- 缺陷主题和退货原因可聚合到 SKU、供应商和批次。

### P3.5

- 至少 3 个真实 SKU 完成一个完整经营周期。
- 预测误差能驱动一次人工确认的选品参数调整。

## 13. 暂不纳入

- 自动改价、自动调广告、自动补货、自动退款和自动发布。
- 全量平台 API 接入。
- 多个 Agent 自由协商。
- 完整 ERP、财务总账和税务系统。
- 公共 SaaS、多租户和复杂 RBAC。
- 没有原始报表和确定性校验的“AI 直接给结论”。

## 14. 建议的第一个开发切片

第一个切片只做 P3.0 和 P3.2 的共同底座：

1. 建立 `sku_stage_events`、`channel_sku_mappings`、`action_cards`。
2. 新增 SKU 360 页面。
3. 支持一份结算 CSV 和一份库存 CSV。
4. 生成实际利润、库存天数和预测差异。
5. 用三条规则生成行动卡片：连续亏损、库存不足、预测偏差。
6. 行动卡片只允许内部查看和人工确认，不接任何外部写接口。

这个切片完成后，系统就能第一次回答：

```text
这个 SKU 现在处于什么阶段？
它实际赚了多少钱？
库存还能卖多少天？
预测错了多少？
下一步应该由谁处理什么？
```
