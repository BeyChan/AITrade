# AITrade 当前方案

> 文档状态：**当前唯一产品方案**。本文同时记录已经落地的能力、当前边界和下一阶段实施计划。文中的“已落地”表示代码和测试已经存在；“规划”表示尚未实现，不能当作现有功能对外宣传。

## 1. 产品定位

产品定位是“个人跨境电商工作流”，稳定后再升级为小团队工作流。目标不是再增加一组报表页面，而是让每个商品都回答四个问题：

1. 现在处在哪个阶段？
2. 当前健康吗？
3. 下一步该做什么？
4. 上一次判断和实际结果差多少？

系统采用“生命周期状态 + 经营域状态”双轴模型。选品、供应商与样品、内容上架可以顺序推进；发布后的广告、库存、客服和财务并行运行，不能强行设计成单线程状态机。

```text
选品验证
→ 供应商与样品
→ 内容上架
→ 发布

发布后并行持续运行：
  广告测试 / 库存物流 / 客服评价
  财务复盘（按结算周期重复）
  → 反哺选品、供应商评分和成本模型
```

### 2.2 部分落地

- 供应商助手只生成内部草稿，支持复制和标记已审阅，**不发送、不联系供应商、不写 `sent_at`**。
- 内容工作台可以手工维护商品事实、图片和 Listing，但**没有 AI Listing 操作员**。
- 平台能力只有本机预检和发布准备队列，**没有真实 dry-run、官方写 Adapter、平台发布或外部回执**。
- 成本模型只有预测利润，**没有实际结算和实际 SKU 利润**。
- 选品阶段有竞品评论分析，但**没有发布后的客服、退货和评价闭环**。

## 3. 产品原则

- 以 SKU 为经营主对象，不以页面或报表为主对象。
- 预测数据与实际数据分开保存，禁止混用；**比较前必须先统一量纲**：同一周期、同一销量、同一币种，并绑定具体 `cost_models` 版本。
- 最终财务数字由确定性计算器产生，AI 只做解释、归类和草稿。
- **以平台结算单为原始事实**：已在净额中扣除的费用不得重复扣减，其余费用只做加回或分摊。
- **个人版以平台后台导出的 CSV/XLSX 为首选数据源**，官方 API 只作为后续增强；不能因为接入慢而阻塞业务闭环。
- 没有真实报表样本验证过的口径，不进入实现排期。
- 每个异常必须绑定指标、原始数据和计算口径。
- 个人版行动卡片保留优先级、截止时间和「确认 + 留痕」；负责人、审批记录和审核人分离属于团队版，本阶段不引入。
- 外部改价、广告预算、补货、清仓、退款和发布始终需要人工确认，系统不自动执行。
- 单编排器 + 专用 Skill；不引入多个 Agent 自由协商。
- 先接 CSV 和人工导出，再逐步接官方 API；不能因为接入慢而阻塞业务闭环。

## 4. 双轴状态模型

### 4.1 生命周期阶段

生命周期轴只描述「商品走到哪一步」，不承载经营结论和周期动作：

```text
validating
→ sampling
→ content_ready
→ listing_ready
→ published
→ operating
→ archived
```

阶段含义：

- `validating`：机会假设、竞品、差评、供应商和报价验证中。
- `sampling`：供应商已定标，样品和合规文件处理中。
- `content_ready`：样品通过，商品定义、图片和 Listing 可以制作。
- `listing_ready`：内容已确认，发布预检通过。
- `published`：已有真实平台发布回执或人工发布记录。
- `operating`：广告、库存、客服和财务数据持续进入。
- `archived`：停止经营，保留历史数据。

两类信息不占生命周期轴，避免和 4.2 的并行经营域状态打架：

- **经营决策结论**（`scaling` 扩大 / `holding` 观察 / `clearing` 清仓退出）记录在 SKU 字段，带决策时间和依据，可随时变化，不触发阶段 transition。
- **财务复盘**是按结算周期重复发生的动作（月度 / 每期结算），不是走一次就离开的阶段；由结算批次驱动，不写入阶段链。

状态变化必须通过受控 transition 完成，并写入 `sku_stage_events`。不能仅通过更新一个字符串字段改变阶段。

### 4.2 经营域状态

发布后，以下域并行运行：

| 经营域 | 状态 |
|---|---|
| 广告 | `not_started / testing / healthy / attention / stopped` |
| 库存物流 | `healthy / low_stock / stockout_risk / overstock / blocked` |
| 客服评价 | `healthy / needs_reply / quality_issue / claim_risk / blocked` |
| 财务 | `pending_data / reconciling / healthy / margin_risk / loss` |

首页和商品 360 页面分别展示生命周期阶段与四个经营域状态，避免把“正在补货”和“广告测试中”错误地合并成一个状态。财务域按结算周期刷新；复盘动作不改变生命周期阶段。

## 5. 八阶段进入与退出条件

| 阶段 | 进入条件 | 必须产出 | 退出条件 |
|---|---|---|---|
| 1. 选品验证 | 有明确市场、平台和品类假设 | 证据包、成本模型、确定性门禁结论 | GO，或明确终止/继续补证据 |
| 2. 供应商与样品 | GO 或人工批准的候选商品 | 定标供应商、样品单、质检报告、合规文件 | 样品通过，资料齐全，供应商可采购 |
| 3. 内容上架 | 样品通过且商品事实已确认 | 商品定义、图片、Listing 版本、预检和发布记录 | 已发布或有可追溯的人工发布回执 |
| 4. 广告测试 | 已发布，有售价、毛利和预算上限 | 单变量实验、每日花费、转化和止损记录 | 达到样本量，输出继续/调整/停止结论 |
| 5. 库存物流 | 已发布，有库存或在途数据 | 可用库存、在途、交期、库存天数和补货建议 | 库存健康，或补货/清仓行动已批准 |
| 6. 客服评价 | 已有订单、评价或售后消息 | 问题分类、退货原因、回复草稿、缺陷标签 | SLA 达标，重复问题进入产品改进池 |
| 7. 财务复盘（周期动作，非阶段） | 有结算、广告、采购、退款和物流费用 | 实际 SKU 利润、现金流、预测差异 | 差异有解释，成本或售价动作已决策；按结算周期重复触发 |
| 8. 反哺选品 | 至少有一个完整经营周期 | 供应商评分、品类经验、预测偏差和规则调整 | 更新下一轮选品参数和成本假设 |

## 7. 数据架构

```text
平台后台 / CSV / 官方 API
→ ingestion_runs + evidence_snapshots
→ 标准化订单、广告、库存、退货和费用事件
→ 确定性指标计算
→ issues（行动卡片字段扩展）
→ 人工确认 / 留痕
→ 执行记录与外部回执（团队版才启用）
→ actual_results
→ forecast_variances
→ 选品、供应商和成本模型反馈
```

### 7.1 复用现有对象

- `product_cases`：选品立项记录
- `products` / `product_market_variants`：商品与国家市场版本
- `channel_listings`：渠道 Listing
- `ingestion_runs` / `evidence_snapshots`：导入批次和原始快照
- `approvals`：外部动作的确认留痕（个人版不启用审批流）
- `issues` / `experiments`：运营异常和实验占位表；**`action_cards` 优先在 `issues` 上扩展业务字段，不另起一张表**
- `cost_models`：**预测的唯一载体**，`forecast_variances` 必须关联具体成本模型版本，否则「预测 vs 实际」无从对齐
- `selection_decisions`：GO / HOLD / NO-GO 结论，是生命周期起点的依据
- `audit_logs`：`sku_stage_events` 沿用其写入与留痕模式
- `supplier_external_ids`：「外部 ID ↔ 内部实体」的现成范式，`channel_sku_mappings` 照此设计
- `economics.ts`：确定性单位经济计算的既有位置，实际利润计算不得另起一套口径

**与现有代码的接缝**：16 项确定性门禁给出 GO → 转 `product_cases` 立项 → 由立项动作创建首条 `sku_stage_events(validating)`；阶段回退必须走受控 transition 并写原因，不允许直接改状态字段。

### 7.3 数据契约

每条导入记录必须保留：

```text
source_code
source_record_id
ingestion_run_id
observed_at
period_start
period_end
currency
raw_hash
marketplace_code        # 站点，决定币种、时区和税费规则
report_timezone         # 报表原始时区，禁止隐式按本地时区解释日期
settlement_id           # 平台结算批次；结算周期常跨月，订单日 != 结算日
fx_rate / fx_rate_date  # 站点币种 -> 本位币的汇率及取值日，不得用实时汇率回填
```

跨境场景必须显式约定：

- **归集口径**：以结算周期（收付实现制）为主账，订单月（权责发生制）为辅账，两套结果分列展示，禁止混用；退款常发生在订单后 1–2 个月，需要在两套口径中各自归属。
- **币种**：站点币种保存原值，本位币金额由 `fx_rate` 换算并保留换算依据；跨站汇总前不合并。
- **时区**：所有 `period_start / period_end` 带原始时区，日粒度指标按站点日历而非服务器日历聚合。

SKU 映射不是线性优先级，而是多对一 + 生效时间：

```text
ASIN / FNSKU / Merchant SKU / 父体变体 / Bundle
→ channel_listings (seller_sku, marketplace_code, valid_from)
→ product_market_variants → products → product_case
```

同一内部 SKU 可对应多条平台标识；映射变更保留生效区间，历史记录按当时的映射解释。无法映射的记录进入待处理队列，不能自动归到某个商品。

### 7.4 真实报表与归一化规则（落地前提）

个人版数据源以平台后台导出为主。接入前必须先确认每类报表的**实际文件、字段和周期**，而不是先建表：

| 报表 | 常见格式 | 周期 | 归一化要点 |
|---|---|---|---|
| 结算单 / Settlement Report | TSV / CSV / XLSX | 平台结算批次（常见约 14 天，跨月） | 以 `settlement_id` 为主键；区分订单、退款、佣金、履约费、广告费、仓储费、调整；净额已扣的费用不得重复扣减 |
| 广告搜索词 / 广告活动报告 | CSV / XLSX | 日 / 周 | 广告销售额有归因窗口（常见 7 天），与结算周期不同期，需单独标注归因口径 |
| FBA 库存 / 预留库存 / 在途 | TXT / CSV | 日快照 | 区分可用、预留、在途、不可售；日均销量需处理新品与断货期 |
| 退货 / 退款报告 | CSV | 日 / 批次 | 关联原订单与结算批次，处理跨期退款 |

**落地前提**：在拿到至少一份真实结算单和一份真实库存快照之前，不创建 `actual_results` / `forecast_variances` 等表，也不实现阈值规则——否则只能用演示数据把口径写死。现有仓库的 4 个 CSV 模板全部是选品 / 供应商 / 报价，尚无任何经营类报表。

## 8. 指标和确定性规则

### 8.1 指标口径

| 指标 | 口径 |
|---|---|
| 实际净销售额 | 以结算单为原始事实：成交收入 − 折扣 − 退款；**佣金、履约费等若已在结算净额中扣除，不得再减一次** |
| 贡献利润 | 净销售额 − 采购/头程与关税摊销 − 平台费 − 履约费 − 广告费 − 退货损失 − 仓储/长期仓储/移除费 − Coupon/Deal 费 − VAT 或销售税 − 汇兑损益 − 其他费用 |
| 实际净利率 | 贡献利润 / 净销售额 |
| ACOS | 广告花费 / 广告带来的销售额；**必须记录归因窗口**，不得与结算周期直接对齐 |
| TACOS | 广告花费 / 总销售额 |
| 盈亏平衡 ACOS | 广告前贡献**毛利率**（对广告销售额），不是绝对金额 |
| 库存天数 | 可用库存 / 最近 28 天日均销量；新品改用 7/14 天窗口，断货期日均销量设下限，促销异常日剔除，须记录所用 fallback |
| 入库覆盖缺口 | 库存天数 − 供应商交期 − 安全库存天数 |
| 退货率 | 退货数量 / 发货数量；按订单月与结算月分别可查 |
| 预测误差 | **先统一量纲再比较**：把 `cost_models` 的单件预测按同一周期 × 实际销量 × 同一币种折算，再算 `(实际 − 折算预测) / |折算预测|`；`|折算预测|` 低于阈值时不出比率，只给绝对差额 |

所有公式由 TypeScript 确定性函数实现，落在 `economics.ts` 既有口径上；模型不得自行计算最终财务数字。**预测来自单件单位经济、实际来自周期总量，直接相减是本方案最容易产生假数的地方。**

口径内核（预测折算、贡献利润、盈亏平衡 ACOS、广告效率、库存天数、周期归集）已在 `src/lib/operations-metrics.ts` 实现并有单元测试，对非有限金额、非法站点日期、结算冲正加回和净额重复扣费均有防护。它只做纯计算，**尚未接入任何真实报表导入，也没有落任何业务表**；所有阈值由调用方传入，未启用默认值。

### 8.2 首批异常规则

阈值必须可按市场、平台、品类配置，不能在代码里写死。

| 规则 | 默认观察窗口 | 输出 |
|---|---|---|
| 连续亏损 | 7 天 | `profit_negative` 行动卡 |
| 实际净利率低于目标 | 14 天 | `margin_below_target` |
| ACOS 高于盈亏平衡 ACOS | 最低点击量 + 7 天 | `ad_waste` |
| 库存覆盖小于交期 + 安全天数 | 每日 | `stockout_risk` |
| 库龄超过阈值 | 30/60/90 天 | `overstock` |
| 退货率突增且缺陷集中 | 7 天对比前 28 天 | `quality_issue` |
| 售后消息超过 SLA | 每小时 | `service_sla` |
| 实际利润与预测偏差超过阈值 | 月度 | `forecast_drift` |

同一条规则只生成一个开放行动卡片，使用指纹幂等。重复导入不能重复报警。上表阈值是占位默认值，必须用真实结算与库存样本校准后才允许启用；未校准时不生成对外行动建议。

## 9. AI Skill 边界

| Skill | AI 负责 | 确定性代码负责 | 人工负责 |
|---|---|---|---|
| 报表映射 | 建议字段映射、解释差异 | Schema、单位、币种、去重和总量校验 | 确认未知字段和映射例外 |
| 样品质检提取 | 从质检文本提取规格和缺陷 | 缺陷分类、阈值、样品状态和证据定位 | 确认样品通过/否决 |
| 广告分析 | 解释搜索词、浪费和实验结论 | ACOS、TACOS、样本量、预算和止损线 | 批准调预算、停投和新建活动 |
| 库存风险 | 解释交期和异常 | 库存天数、补货点、在途和现金占用 | 批准补货、清仓和采购 |
| 客服分诊 | 分类问题、提取缺陷、生成回复草稿 | SLA、风险关键词、责任归属和重复问题检测 | 批准外部回复、退款和索赔 |
| 财务差异 | 解释预测与实际差异 | 利润、费用、退款和现金流计算 | 确认调账和修改成本假设 |
| 反哺分析 | 总结品类和供应商经验 | 样本量、成功率、偏差和评分计算 | 确认更新选品规则 |

AI 输出统一包含：

```json
{
  "summary": "",
  "evidenceRefs": [],
  "affectedEntities": [],
  "recommendedActions": [],
  "confidence": 0,
  "requiresReview": true
}
```

没有证据引用、指标口径或业务规则的结果不得写入业务表。

## 10. 行动卡片

所有异常统一转成 `issues` 上的行动卡片扩展，不再分散在不同页面里，也不另起 `action_cards` 表。

### 10.1 状态

```text
open
→ reviewing
→ approved | rejected
→ executing
→ done | expired
```

以上是**团队版**完整状态机；个人版只保留 `open → done`，中间记录确认时间、结论和备注，不引入 reviewing / approved / executing。

### 10.2 字段

- `action_type`
- `severity`
- `case_id` / `channel_listing_id`
- `title` / `reason`
- `metric_snapshot`
- `evidence_refs`
- `recommended_action`
- `expected_impact`
- `guardrails`
- `owner`（团队版；个人版留空）
- `due_at`
- `confirmation_id`（个人版确认留痕；团队版才用 `approval_id`）
- `rollback_plan`

### 10.3 风险分级

- L0：只读分析和内部草稿，可自动生成。
- L1：内部任务、提醒和整改单，可自动创建但需要人工确认。
- L2：改价、广告预算、补货、清仓、客服外部回复，必须人工确认；系统只生成建议，不执行。
- L3：采购付款、退款、赔付、法律和合规结论，禁止自动执行。

## 11. 分阶段交付

工期按单人或一到两人小团队估算，真实样本验收时间另计。

**排期原则调整**：原计划按「底座 → 样品 → 财务 → 广告 → 客服 → 反哺」横向铺开，等于先建 18 张表再验证假设。改为**先跑通一条能用真实报表验证的财务闭环**，再按验证结果决定是否扩展。P3.1–P3.5 是目标设计，在 P3.0 用真实样本跑通之前不进入实现排期。

### P3.0 数据契约与财务闭环（第一个交付）

目标：让系统第一次回答「这个 SKU 实际赚了多少钱、和当初预测差多少」。

前置条件：

- 拿到至少一份真实结算单和一份真实库存快照，按 7.4 确认字段与周期。
- 按 7.3 补齐站点、时区、结算批次、汇率字段；按 8.1 校准口径。

交付：

- 两种报表的导入与归一化，复用 `ingestion_runs` / `evidence_snapshots`
- `sku_stage_events`、`channel_sku_mappings`，以及 `issues` 的字段扩展（不新建 `action_cards`）
- 按 SKU × 结算周期归集实际贡献利润，与 `cost_models` 具体版本对齐，输出预测差异
- 在现有 `/cases/[id]` 增加一块展示，**不新增 SKU 360 等独立页面**

完成定义：

- 用一份真实结算单能算出 SKU 月度贡献利润，且每笔可回溯到原始快照与结算批次。
- 预测差异的单位、周期、币种与预测侧一致，不出现量纲错配。
- 跨期退款、汇率、已扣费用三项各有明确处理规则且可复算。

**本阶段不做**：行动卡片状态机、审批流、广告/客服/反哺域、五张新页面、真实平台写接口。

### P3.1 供应商与样品闭环

交付：

- 样品申请、收样、质检、缺陷和结论
- 认证与合规文件归档
- 样品通过后才能解锁内容制作
- 供应商报价、交期、次品率和响应评分

完成定义：

- 样品状态可追溯。
- 未通过样品或缺合规文件时不能进入内容阶段。
- 供应商评分可由实际报价和质检结果更新。

### P3.2 实际利润与库存

交付：

- 结算、库存、物流费用和退货 CSV
- `actual_results`、`inventory_snapshots`、`forecast_variances`
- 库存天数、补货点和利润差异规则
- 财务与库存行动卡片

完成定义：

- 任意导入指标可以追溯到原始快照。
- 实际利润和预测利润分开展示。
- 库存覆盖不足能生成补货建议，但不自动下单。

### P3.3 广告测试

交付：

- 广告活动、搜索词和每日花费导入
- 单变量实验、预算上限、止损线和样本量
- ACOS、TACOS、盈亏平衡 ACOS
- 继续/调整/停止的行动建议和人工确认

完成定义：

- 每个实验只能改变一个变量。
- 实验结论可追溯到指标快照。
- 不会自动调预算或停投。

### P3.4 客服、评价和退货

交付：

- 售后消息、评价、退货原因和缺陷分类
- 回复草稿、SLA、升级和退款边界
- 重复缺陷进入产品改进池
- 供应商责任和售后评分

完成定义：

- 高危关键词不会自动外发。
- 退货原因可以按 SKU 和供应商聚合。
- 重复质量问题能反哺供应商与选品规则。

### P3.5 反哺与团队协作（团队版，个人工作流阶段不实现）

交付：

- 预测误差、供应商评分和品类经验
- 选品参数和成本模型的人工确认更新
- Owner / Reviewer / Operator 基础角色
- 任务分派、评论、通知和审核分离

完成定义：

- 每个实际经营结果都能解释对选品参数的影响。
- 高风险动作提交人与审核人可分离。
- 经营经验不会只留在某个人的记忆里。

## 12. 验收指标

### P3.0

- 至少 1 份真实结算单 + 1 份真实库存快照完成导入，字段映射可复现。
- SKU × 结算周期的贡献利润每笔可回溯到原始快照、结算批次与汇率依据。
- 预测差异与 `cost_models` 版本绑定，量纲一致性有测试覆盖。
- 活跃 SKU 阶段覆盖率 100%、阶段变化审计覆盖率 100%（沿用原有目标）。

### P3.1

- 样品从申请到结论的状态完整率 100%。
- 样品、合规和供应商资料可从 SKU 360 追溯。

### P3.2

- 结算、库存、退货报表关键字段映射时间小于 10 分钟。
- 实际利润与预测利润可按 SKU、渠道和月份追溯。
- 未知 SKU 映射不能静默写入。

### P3.3

- 广告实验结论可复现。
- 任何预算调整都必须有批准记录和回滚方案。

### P3.4

- 售后消息 SLA 可统计。
- 缺陷主题和退货原因可聚合到 SKU、供应商和批次。

### P3.5

- 至少 3 个真实 SKU 完成一个完整经营周期。
- 预测误差能驱动一次人工确认的选品参数调整。

## 13. 暂不纳入

- 自动改价、自动调广告、自动补货、自动退款和自动发布。
- 全量平台 API 接入。
- 多个 Agent 自由协商。
- 完整 ERP、财务总账和税务系统。
- 公共 SaaS、多租户和复杂 RBAC。
- 没有原始报表和确定性校验的“AI 直接给结论”。

## 14. 建议的第一个开发切片

**切片 = 一条端到端的最窄链路**：不先建完所有表、也不先做完所有页面，而是从数据进来 → 落库 → 计算 → 页面显示，每层只做够用的一小块，一次打通一条竖线，用来最快验证「这套口径到底成不成立」。

当前第一个切片按 P3.0 执行，顺序是**先定口径、再接数据、最后才算数**：

1. 拿到真实结算单和库存快照，按 7.4 确认字段、周期、时区和归一化规则。
2. 按 7.3 补齐导入契约（站点、时区、结算批次、汇率），按 8.1 校准口径与 fallback。
3. 复用 `ingestion_runs` / `evidence_snapshots` 完成两种报表的导入，保留原始快照。
4. 落 `sku_stage_events`、`channel_sku_mappings` 和 `issues` 字段扩展，不新建独立表。
5. 按 SKU × 结算周期归集实际贡献利润，与 `cost_models` 版本对齐，输出预测差异。
6. 在现有 `/cases/[id]` 展示结果；不生成行动卡片，不接任何外部写接口。

**开工门槛**：第 1 步没完成之前不建表、不写阈值规则——真实字段没确定，写出来的映射和阈值只能靠猜。

这个切片完成后，系统就能第一次回答：

```text
这个 SKU 现在处于什么阶段？
它实际赚了多少钱？
和当初的预测差多少，差在哪个口径？
库存还能卖多少天？
```

「下一步应该由谁处理什么」留到团队版；个人版只需要「下一步做什么」。
