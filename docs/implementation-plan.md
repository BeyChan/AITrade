# AITrade 实施蓝图

> 文档状态说明：**P2.0 AI 证据收件箱和 P2.1 内部供应商草稿已实现**。P2.1 当前支持 RFQ、缺失信息追问和报价到期提醒三类内部草稿，不支持报价单图片/截图/PDF OCR，也没有邮件/IM 发送或供应商自动联系能力。P2.2 及之后仍是规划。代码测试通过不代表真实业务样本验收已经完成。

## 0. 当前实现状态（P2.0 + P2.1 内部草稿）

当前仓库已经实现一条可运行的本地纵向切片：

```text
AI 选品假设（模板 / Ollama / OpenAI-compatible）
→ 加入验证并生成竞品、差评、专利、物流、供应商和报价待办
→ 真实证据、供应商短名单与报价
→ AI 证据收件箱：文本 / CSV / JSON / Markdown 候选字段提取
→ 人工审核字段并事务应用
→ 竞品快照、供应商短名单与报价、评论证据落库并重算确定性门禁
→ 16 项确定性 GO / HOLD / NO-GO 门禁
→ 仅 GO 可转商品立项并导入全部报价
→ AI 供应商助手：基于已录入事实生成 RFQ / 追问 / 到期提醒内部草稿
→ 人工审阅并复制，外部沟通由人在系统外部完成（系统不发送）
→ 候选品 / 供应商 / 报价 CSV 或人工接入
→ 导入运行、幂等去重与证据快照
→ 可选 Keepa ASIN 只读同步
→ Amazon / Shopify / eBay 只读连接诊断与审计
→ 证据占位与确定性单位经济模型
→ 商品机会看板
→ 成本模型版本化与人工立项
→ 人工录入供应商报价
→ 到岸成本、综合评分与风险提示
→ 人工定标并回写新成本版本
→ 商品定义
→ 主图上传与逐项人工检查
→ Listing 草稿版本化与确定性预检
→ 多国家 × 多平台渠道目标
→ 平台字段映射与独立市场版本
→ 人工内容确认
→ 确定性发布准备门禁（8 项检查）
→ 人工发布队列确认（仅内部队列）
→ 审计时间线
```

已实现的能力边界：

- `/` 首页只负责新建研究；`/ai-sourcing` 是 AI 选品下的独立批次列表，完整展示所有国家 × 平台的批次并支持删除，不新增主导航入口。删除会级联研究假设、证据、供应商短名单和报价，但保留已转商品立项的商品及后续数据，并写入 `ai_sourcing.batch_deleted` 审计。
- 研究创建仍按国家 × 平台隔离，每次生成 5 个不重复机会假设、研究优先级、加入验证与结果持久化；表单提交显示 pending 状态，服务端以 `request_key` 唯一索引保证重复点击或网络重试复用同一批次。
- AI Provider 默认使用免 Key 模板，也可配置 Ollama 或 OpenAI-compatible；模型失败自动回退模板，AI 不生成虚假市场事实。
- `/ai-inbox` 已实现文本、CSV、JSON、Markdown 的任务创建、字段提取、来源定位、置信度与冲突校验、人工审核、失败重试和幂等复用；它不再是一级导航，而是从机会验证页带 `targetHypothesisId` 进入的上下文工具。
- 机会验证页提供“AI 智能录入”入口并显示待审核、提取中和失败计数；审核应用成功后自动返回对应机会，重新计算门禁并展示结果。侧边栏按实际业务流程动态组织，不固定入口数量；一级入口跟随业务阶段，连接与设置作为工具入口，真实二级页面存在时才挂载子入口。
- AI 证据任务只写入暂存表；应用时服务端重新读取字段并校验，在事务中写入竞品、供应商报价或评论证据，再重算目标机会的确定性门禁。
- 敏感字段、无来源、来源无法定位、冲突、币种不一致和非法值均阻止自动应用；AI 不直接写 GO / HOLD / NO-GO。
- AI 供应商助手已在 `/ai-sourcing/[runId]` 接入，可基于已录入的商品、供应商和报价事实生成 RFQ、缺失信息追问与报价到期提醒内部草稿。模型只能润色主题和开场，缺失问题始终由确定性代码追加；草稿可复制并标记 `reviewed`，但没有发送入口，审计固定记录 `externalActions: none`、`sent: false`。
- 当前不支持图片、截图和 PDF OCR，不自动联系或发送消息给供应商，不定标、不采购、不付款、不改价、不发布。
- 真实竞品、差评、专利、物流、供应商、报价和汇率依据均持久化来源 URL、观察时间、录入人和原始证据；非 USD 站点缺可追溯汇率时为 HOLD。
- 16 项确定性门禁覆盖研究分、竞品、差评、供应商、报价、到岸成本、净利率、压力利润、证据完整度、MOQ、交期、样品评分、专利、物流、首单现金和汇率。
- 只有确定性 GO 可转商品立项；转入会复制全部供应商、`quote_received` RFQ 占位、报价和证据，`sent_at` 保持为空并继续进入供应商比价与人工定标。
- 统一数据源工作台和 `/api/ingestion` 已支持候选品、供应商、报价与 Keepa 通道。
- CSV 导入会写入 `ingestion_runs`、`evidence_snapshots`，并保留来源、记录 ID 和采集时间。
- 供应商按平台 + 外部 ID、规范化链接或名称归一化去重；报价按规范化哈希幂等去重。
- Keepa 是可选只读 Adapter；没有 `KEEPA_API_KEY` 时返回 409，不发起外部请求，不伪造数据。
- `/connections` 与 `/api/connections/check` 提供平台只读授权诊断；Amazon 验证 LWA + Seller API，Shopify 验证自有店铺读取，eBay 只验证应用凭证。
- 连接检查写入 `connector_health_checks` 和 `connector.health_checked` 审计；不保存或返回 Secret、Refresh Token、Access Token。
- TikTok Shop 和 1688 仍标记为 `unsupported`，不发起外部请求；eBay 应用凭证成功不代表卖家 OAuth 已验证。
- 确定性单位经济模型、成本版本、人工立项和审计日志已经打通。
- 供应商与报价由人工录入；到岸成本、压力情景利润和评分由确定性代码计算。
- 少于 3 家有效报价仍可定标，但必须填写定标说明；系统推荐不能替代人工决策。
- 定标后锁定新增报价和重复定标，并生成新的成本模型版本。
- 只有完成供应商人工定标的商品才能进入内容工作台。
- 商品定义由人保存，内容包括商品名称、目标用户、核心差异点、规格、包装和禁用声明。
- 主图仅接受真实 JPG / PNG / WebP，最大 8 MB；文件保存到本地受控目录，并通过应用接口读取。
- 主图必须由人确认背景、商品完整性、无未授权文字/水印以及分辨率与画质。
- Listing 每次保存都会创建新版本；确定性预检检查长度、完整性、搜索词 UTF-8 字节和常见高风险声明。
- 内容确认要求预检无错误，并至少有一张通过人工检查的主图；确认人、说明、预检结果和图片 ID 都会留痕。
- `content_approved` 只表示某个国家 × 平台版本通过内部内容门禁，不是 `published`，不会调用平台 API 或产生任何外部发布动作。
- 同一商品可以创建多个国家 × 平台目标；每个目标有独立的 locale、currency、Listing 版本、平台 payload 和预检结果。
- 已内置 Amazon、Shopify、TikTok Shop、eBay、CSV / 人工的本地字段映射；渠道目标仍使用 `unconfigured` 的本地测试店铺，外部 ID 保持为空。
- 渠道发布准备由确定性代码计算，状态包括 `blocked`、`local_ready`、`dry_run_unsupported`、`approval_pending`、`approved_for_publish`；检查覆盖最新版本、本地预检、内容确认、主图检查、正式店铺、官方写 Adapter、真实平台 dry-run 和当前版本发布队列确认。
- `channel_launch_reviews` 绑定当前渠道 Listing 版本，并固化检查快照、确认人、说明与决策；只有 `approval_pending` 且无阻断项时才能写入。
- 发布队列确认只表示确认进入内部队列，不是平台发布。当前所有平台的 `dryRunSupported` 和 `publishingSupported` 均为 `false`，所有检查和确认结果固定记录 `externalActions: none`、`published: false`，外部商品 ID 保持为空。

为保持现有数据模型简单，商品主状态在立项后仍保持 `approved`。供应商定标由 `supplier_selections` 表达，内容确认状态由 `listings.status` 和 `listing_reviews` 表达；后续扩展完整状态机时再统一迁移。

尚未实现：图片/截图/PDF OCR、报价单视觉解析、邮件与 IM 自动归档、供应商回复解析、评论/关键词和竞品证据的规模化自动采集、RFQ 外部发送、样品/质检、AI 图片生成、A+ 自动排版、品牌授权自动核验、密钥托管、eBay 卖家 OAuth、平台类目与必填字段校验、真实平台 dry-run、官方写 Adapter、发布、改价、库存同步、广告操作和运营复盘。RFQ、追问和到期提醒目前只生成内部草稿，不发送。Amazon SP-API 与 Shopify 只完成只读授权诊断，eBay 只完成应用凭证诊断；TikTok Shop 和 1688 尚未接入。所有平台均没有真实外部写连接。当前版本没有登录、角色权限和多租户能力，不能直接作为生产系统使用。

## 1. 落地原则

1. **先做运营工作台，不做另一个全功能 ERP。**
2. **先跑通一条纵向链路，不先做全链路大平台。**
3. **确定性计算用代码，判断和生成用模型。**
4. **所有 Agent 输出必须是结构化产物，不能只有聊天记录。**
5. **有外部副作用的动作默认需要人工确认。**
6. **优先官方 API；网页自动化只作为无 API 时的兜底。**
7. **每个结论必须保留来源、时间、版本和置信度。**
8. **AI 优先替代录入、整理、草稿和监控，不替代最终商业判断。**
9. **采用单编排器 + 专用 Skill，不做多个 Agent 自由协商。**
10. **先测量人工耗时，再按真实节省的时间决定下一项自动化。**

## 2. 初始假设

- 首发平台：Amazon 美国/日本站。
- 首发类目：宠物用品（与参考视频一致，但系统不写死类目）。
- 团队：1～5 人，小团队运营。
- 第一版采用半自动模式：AI 生成报告和草稿，人做关键决策。
- 独立站以后可接 Medusa；Amazon 主战场不把 Medusa 当中枢。

## 3. 产品形态

### 3.1 商品机会看板

按阶段展示每个商品机会：

```text
发现 → 初筛 → 立项 → 询价 → 打样 → 商品定义
→ 内容制作 → 待发布 → 运营中 → 已归档 / 已否决
```

每张卡片展示：

- 当前阶段和负责人
- 市场、类目、目标售价
- 基准/压力情景净利润
- 证据完整度
- 未解决风险
- 下一步动作
- 最近一次确认记录

### 3.2 任务与操作记录

- Agent 完成的分析和生成结果进入任务中心。
- 人可以确认、驳回、要求补充证据。
- 高风险动作单独形成确认单。
- 所有状态变化写入审计日志。

### 3.3 资产库

统一管理：

- 竞品与市场证据
- 供应商报价和附件
- 样品/质检记录
- 原始产品图、主图、场景图、A+ 图
- Listing 草稿和平台版本
- 广告实验记录

## 4. MVP 纵向切片

### 4.1 输入

P1.0 已支持候选品 CSV 文件上传或文本粘贴。推荐字段：

```text
source, source_record_id, observed_at, asin, marketplace, category,
title, url, competitor_price, currency, monthly_sales_min,
monthly_sales_max, review_count, rating, bsr, keyword,
keyword_search_volume, seller_count, variation_count, landed_cost,
fba_fee, referral_rate, ad_rate, return_rate, return_processing,
return_recovery_rate, coupon, storage_cost, other_cost, notes
```

供应商和报价也分别支持 CSV 导入；报价必须关联已人工立项的商品。没有官方 API 或尚未取得授权的渠道继续使用可追溯 CSV/人工通道，避免把项目卡在接口权限上，同时禁止用未授权爬虫或伪造数据绕过接入。

### 4.2 AI 辅助选品与立项（P1.3 已实现）

AI 负责扩大假设空间，确定性代码负责是否放行。当前可运行路径：

1. 在当前国家 × 平台输入类目和简报，固定生成 5 个不同方向。
2. 人工选择方向加入验证，系统生成竞品、差评、专利、物流、供应商和报价待办。
3. 人工录入带来源 URL、观察时间、录入人和原始快照的真实证据。
4. 人工录入供应商短名单和至少 3 家真实报价。
5. 系统执行 16 项确定性门禁，输出 GO、HOLD 或 NO-GO。
6. 只有 GO 可转商品立项；全部报价和证据随立项复制，继续进入人工比价与定标。

目标态系统执行：

1. 归一化候选品数据。
2. 采集可获得的竞品、关键词、评论和社媒证据。
3. 提取评论主题、差评原因、用户需求和对产品动作。
4. 运行确定性单位经济模型。
5. 生成证据包、风险清单和 GO/NO-GO 建议。
6. 人审立项。

必须输出：

- `selection_report`
- `evidence_snapshot`
- `cost_model`
- `risk_list`
- `decision_recommendation`

### 4.3 供应商 RFQ 与人工定标

用户确认立项后：

1. 生成 RFQ 包：规格、目标成本、MOQ、认证、包装、交期要求。
2. 从供应商库/人工导入名单中选择 3～5 家。
3. 导出询价单或通过可用渠道发送。
4. 录入报价、MOQ、交期、账期、认证和样品费用。
5. 生成报价对比和供应商评分卡。
6. 人审确定供应商；打样、定样和质检进入下一阶段。

第一版不把“自动给阿里供应商打电话”作为必做项。

当前 P1.3 已实现 AI 选品阶段的供应商短名单、真实报价、确定性门禁、GO 转立项，以及立项后的 CSV/人工报价、幂等去重、来源快照、评分对比、人工定标和成本回写。P2.1 已在机会详情中增加 RFQ、缺失信息追问和报价到期提醒内部草稿，但不负责外部发送。转立项时创建 `quote_received` RFQ 占位记录；人工录入同样使用 `quote_received`，CSV 导入使用 `quote_imported`，三者 `sent_at` 都保持为空，表示没有发送证据。RFQ 外部发送、PDF 导出和邮件/IM 自动归档仍未实现，审计记录 `externalActions: none`、`rfqSent: false`。

### 4.4 商品定义、主图与 Listing 内容（P1.0 已实现）

目标态是在样品与合规通过后进入内容制作。当前 P1.0 为缩短验证路径，允许完成供应商人工定标后直接进入内容工作台；样品、质检、定样和认证文件归档仍是后续能力。

当前已落地：

1. 人工保存商品定义：商品名称、目标用户、核心差异点、规格材质、包装清单、禁用声明和编辑人。
2. 上传一张主图。服务端校验文件头、MIME、扩展名和大小，只接受 JPG / PNG / WebP，最大 8 MB，并保存到本地受控目录。
3. 人工确认白底或纯色背景、商品完整、无未授权文字/水印、分辨率与画质；系统记录检查人、说明和审计日志。
4. 人工保存 Listing 草稿，包括品牌、标题、五点描述、商品描述和后台搜索词。
5. 每次保存 Listing 都创建新版本，保留旧版本和对应的自动预检结果。
6. 确定性预检通过且至少一张主图通过人工检查后，允许记录人工内容确认。

当前不自动生成图片或 Listing 文案，不做 A+ 排版、品牌授权核验、知识产权判断、认证文件校验或平台类目必填字段校验。人工内容确认也不触发平台发布。

### 4.5 确定性发布预检（P1.0 已实现，非平台发布）

当前预检完全在本地运行，不调用外部平台接口。已检查：

- 标题非空、长度上限和过短提示。
- 五条卖点是否完整、是否超过长度上限、是否重复。
- 商品描述是否为空或超过长度上限。
- 后台搜索词是否为空、UTF-8 字节上限和分隔符提示。
- 品牌是否为空，以及品牌名是否出现在商品描述中。
- “最佳、第一、保证、治愈、100%、零风险”等常见高风险或绝对化表述。
- 内容确认前再次确认预检无错误，并确认存在已通过人工检查的主图。

预检评分用于展示和排序风险，不代替真实合规检查。以下仍未实现：

- Amazon 类目必填字段、变体关系和属性映射
- SP-API dry-run、与现有 Listing 的冲突检查
- 平台图片规格的自动核验
- 品牌授权、知识产权、认证文件和类目准入自动核验
- 平台 payload 的最终合法性、价格与库存一致性和真实 dry-run
- 平台发布、改价、库存同步、广告及任何外部写操作

发布必须继续保留人工确认和审计记录；在当前版本中，系统只能把特定渠道版本标记为 `content_approved`，不能标记为 `published`。

### 4.6 多国家、多平台适配层（P1.0 已实现）

P1.0 把“商品事实”和“渠道版本”拆开：

```text
product_cases
→ products
→ product_market_variants（国家 / locale / currency）
→ channel_accounts（平台店铺，当前 unconfigured）
→ channel_listings（国家 × 平台目标）
→ channel_listing_versions（独立版本、payload、预检、确认）
```

已实现的适配能力：

- Amazon：输出 SP-API 形状的 marketplace、locale、currency 与 attributes。
- Shopify：输出 draft product、handle、tags 和 HTML 描述。
- TikTok Shop：输出标题、描述、selling points、locale 和 currency。
- eBay：输出占位 draft payload，并显式提示 Sell API 未连接。
- CSV / 人工：输出人工核对字段，不执行导出。
- 每个平台可以使用不同的长度、卖点数量、关键词字节和高风险声明规则。

当前边界：适配器只做本地字段转换和预检，不包含认证、签名、限流、重试、幂等发布、回执对账或平台错误映射。真实接入时必须把凭据放在密钥管理系统中，禁止在数据库明文保存卖家后台密码、Cookie 或长期 API secret。

### 4.7 平台只读连接诊断（P1.1 已实现）

连接中心先解决“凭证能否安全访问自有店铺”，再考虑任何写动作：

```text
.env.local / 密钥管理
→ 只读诊断
→ connector_health_checks
→ connector.health_checked 审计
→ 人工验收
→ 本地内容门禁与发布准备检查
→ 正式店铺 + 官方写 Adapter + 平台 dry-run（后续）
→ [人审] 确认进入内部发布队列（P1.1 已实现）
→ 幂等写入与外部回执（后续）
```

已支持：

- Amazon SP-API：使用 LWA refresh token 换取短时 access token，调用 `sellers/v1/marketplaceParticipations` 验证自有店铺与市场访问；区域支持 `na`、`eu`、`fe`。
- Shopify Admin API：只调用 `shop.json` 读取店铺名、币种和国家；域名必须是 `*.myshopify.com`，API 版本使用 `YYYY-MM`。
- eBay：只调用 client credentials token 端点验证应用凭证；卖家 OAuth 和 Sell API 权限没有验证。
- TikTok Shop / 1688：没有实现诊断，返回 `unsupported` 且 `externalRequestAttempted: false`。

安全与审计约束：

- 缺少必需配置时返回 `409 not_configured`，不发起外部请求。
- 所有外部请求超时为 15 秒。
- 健康记录只保存状态、验证层级、耗时、检查人和非敏感详情。
- 审计记录 `connector.health_checked`，包含 `externalActions` 和 `credentialsExposed: false`。
- 诊断成功不等于发布权限、类目合规或平台 dry-run 通过；当前写连接数量固定为 0。

### 4.8 发布准备门禁与内部发布队列（P1.1 已实现）

发布准备由确定性代码计算，不依赖模型自由判断。每次检查评估以下 8 项：

```text
LATEST_VERSION
LOCAL_PREFLIGHT
CONTENT_APPROVED
MAIN_IMAGE_APPROVED
PRODUCTION_ACCOUNT
WRITE_ADAPTER
PLATFORM_DRY_RUN
VERSION_LAUNCH_APPROVAL
```

状态机按以下顺序收敛：

| 状态 | 条件与含义 |
|---|---|
| `blocked` | 最新版本、本地预检、内容确认或主图检查仍有缺口 |
| `local_ready` | 本地内容检查通过，但还没有连接非演示的正式平台店铺 |
| `dry_run_unsupported` | 店铺条件满足，但官方写 Adapter 或真实平台 dry-run 不可用 |
| `approval_pending` | 全部前置检查通过，等待人工确认进入内部发布队列 |
| `approved_for_publish` | 当前版本已人工确认进入内部发布队列，仍未调用平台发布接口 |

确认约束：

- 确认动作必须在服务端重新计算最新状态，只接受 `approval_pending` 且阻断项为 0 的版本。
- 确认记录写入 `channel_launch_reviews`，绑定 `channel_listing_id` 与 `channel_version_id`；旧版本确认不能复用于新版本。
- 记录确认人、说明、检查快照与决策，并写入 `channel.launch_readiness_checked`、`channel.launch_queue_approved` 审计动作。
- `WRITE_ADAPTER` 和 `PLATFORM_DRY_RUN` 必须分别验证。本地预检通过不能冒充平台 dry-run。
- 当前所有平台均为 `dryRunSupported=false`、`publishingSupported=false`，所以真实路径最多到达 `dry_run_unsupported`；`approval_pending` 与 `approved_for_publish` 只是为后续官方能力预留的受控状态。
- 所有发布准备结果和队列确认固定保持 `externalActions=none`、`published=false`。`approved_for_publish` 不生成平台 Listing ID，也不代表商品已上架。

## 5. 工作流实现方式

### 5.1 采用“单编排器 + 专用 Skill”，不是自主多 Agent

目标不是创建一群会互相聊天的 Agent，而是把一个人工流程拆成可测试、可重试、可审计的固定步骤：

```text
单一编排器 / Workflow
→ 专用 Skill（模型调用）
→ JSON Schema 与业务规则校验
→ 确定性计算或冲突检测
→ 人工审核例外
→ 事务性写入领域表
```

四类 AI 工作流的职责边界如下。P2.0 已实现证据收件箱的文本输入版本；P2.1 已实现供应商草稿的第一阶段，其余能力仍按阶段推进：

| 工作流 | 模型负责 | 确定性代码负责 | 人负责 | 状态 |
|---|---|---|---|---|
| AI 证据收件箱 | 识别文本证据类型、提取字段、生成缺失项提示 | Schema 校验、来源绑定、去重、冲突检测、计数和门禁计算 | 确认低置信度字段、冲突字段和高风险事实 | P2.0 已实现；OCR/PDF 未实现 |
| AI 供应商助手 | 基于已录入事实润色 RFQ、追问和到期提醒的主题与开场 | 确定性模板、缺失问题追加、事实快照、数字与越权表述校验、幂等和审计 | 复核并复制草稿、外部发送、供应商定标、首单采购 | P2.1 第一阶段已实现；OCR/PDF 与发送未实现 |
| AI Listing 操作员 | 生成标题、卖点、描述、搜索词、本地化版本和图片需求 brief | 平台长度/必填字段/禁用词检查、payload 构造、本地预检 | 确认商品事实与合规声明、批准发布 | P2.2 规划 |
| AI 运营分析员 | 解释报表差异、总结异常、生成行动建议 | 利润核算、广告花费对账、库存阈值、异常规则和排序 | 批准改价、广告预算、补货、清仓等外部动作 | P2.3 规划 |

这里的“多 Skill”不等于“多 Agent 自主协作”：

- UI / API 每次只创建一条 `ai_task`，由同一个编排器决定执行顺序。
- Skill 之间只通过数据库中的结构化产物交接，不通过自由文本互相“讨论”。
- 每个步骤都有输入版本、Prompt 版本、模型版本、Schema 版本、超时和重试上限。
- 某个 Skill 失败时保留失败状态和原始输入，不自动让另一个 Agent 猜一个结果。
- 只有 OCR、图片理解等资源需求明显不同，才拆成独立 Worker；业务流程和审批状态仍然只有一个事实来源。
- 后续如果需要并行执行多个 Skill，是“并行任务”，不是“多个 Agent 自行决定目标”。

### 5.2 AI 任务状态与人工接管

统一任务状态：

```text
queued
  ↓
running ─────────────→ failed
  ├─→ ready ──────────→ applied
  └─→ needs_review ───→ ready ─→ applied
```

- `queued`：任务已持久化，尚未开始。
- `running`：正在解析文本或调用模型；页面不得阻塞等待。
- `needs_review`：存在低置信度、冲突、缺失来源或高风险字段。
- `ready`：所有必填字段均已自动接受或人工接受，且应用前校验没有阻断项。
- `applied`：已经在一个数据库事务中写入竞品快照、供应商短名单/报价、评论证据或对应机会证据表。
- `failed`：解析、模型、Schema 或应用失败；保留错误和原始证据。

字段状态为 `extracted`、`auto_accepted`、`needs_review`、`accepted`、`rejected`、`missing`。人工动作是字段级的 `accept | correct | reject`，不存在任务级的 `approved`、`rejected` 或 `cancelled` 状态。

执行规则：

1. 原始文本或文件内容先写入 `ai_task_artifacts`，再创建 AI 任务。
2. 模型输出先进入 `ai_extracted_fields` 等暂存表，不得直接写业务表。
3. 重试只创建新的 `attempt`，不覆盖历史输出。
4. 任务创建使用 request hash 幂等；重复提交复用同一任务，重复应用返回已应用结果，不能产生重复业务记录。
5. 应用失败时整体回滚，任务回到可重试状态并记录错误。
6. 源文件变化时创建新任务，不修改旧任务的证据链。
7. 应用时必须重新读取数据库中的字段、来源和目标机会，不信任页面提交值。

### 5.3 Dify 的定位

Dify 可用于：

- Prompt 试验。
- 知识库检索。
- 单个 Skill 的原型验证。
- 对比不同模型对同一批样本的提取效果。

但 Dify 不作为数据库、确认系统或最终业务状态的唯一来源。业务数据、字段决策、人工审批和审计必须掌握在自己的数据库中。

### 5.4 字段级结构化输出契约

模型只返回结构化提取结果，不返回“看起来像结论”的自然语言。金额保留原文，由确定性代码归一化为最小货币单位：

```json
{
  "documentType": "supplier_quote",
  "fields": {
    "unitPrice": {
      "value": "18.50",
      "confidence": 0.96,
      "sourceQuote": "单价 18.5 元，MOQ 500"
    },
    "moq": {
      "value": 500,
      "confidence": 0.98,
      "sourceQuote": "单价 18.5 元，MOQ 500"
    }
  },
  "notes": "缺少报价有效期",
  "warnings": []
}
```

硬性规则：

- 每个字段必须有字段名、原值、来源引用和置信度；规范化值与来源位置由服务端计算并持久化。
- 当前文本证据的来源引用必须能在 artifact 原文中定位；图片和 PDF 的页码/OCR block 定位属于后续能力。
- 模型不能决定字段状态；`auto_accepted / needs_review / rejected / missing` 由服务端根据 Schema、来源、冲突、敏感性和置信度计算。
- 模型返回未知字段、缺失必填字段、非法金额或无法映射的币种时，Schema 校验失败，不生成替代值。
- 模型不得把“没有看到”推断为“0”“无风险”或“已认证”。
- 解析失败返回空候选和明确错误；空白字段保持空白，不进入后续门禁。
- 当前保留 provider、model、attempt、耗时、输入字符数、脱敏后的响应摘要和错误；Prompt 独立版本号与 token/费用核算属于后续增强。

### 5.5 AI 证据收件箱（P2.0 已实现）

入口位于机会验证上下文：机会卡片 → `/ai-inbox?targetHypothesisId=...` → 审核与事务应用 → 返回该机会。`/ai-inbox` 的独立全量队列仅作为备用入口保留，不占主导航。

```text
文本 / CSV / JSON / Markdown
→ 保存原始 artifact
→ 创建 ai_task
→ 确定性解析；配置模型时进行结构化提取
→ Schema / 来源 / 冲突 / 去重校验
→ auto_accepted + 人工确认队列
→ 服务端重新校验并事务性应用
→ 审计与门禁重算
```

当前应用目标：

- 竞品证据：`competitor_snapshots` + `opportunity_evidence`。
- 供应商报价：`supplier_shortlists` + `sourcing_supplier_quotes` + `opportunity_evidence`。
- 评论证据：`review_insights` + `opportunity_evidence`。
- 任务、字段、来源与审计：`ai_tasks`、`ai_task_artifacts`、`ai_extracted_fields`、`ai_field_sources`、`ai_review_actions`、`ai_model_calls`、`audit_logs`。

后续接入主数据表时必须继续复用现有数据链路：

- `ingestion_runs`：记录批量导入的来源、状态、数量、告警和完成时间。
- `evidence_snapshots`：保存原始文本、文件信息、内容哈希和观察时间。
- `suppliers` / `supplier_external_ids`：承接已确认的供应商。
- `quotes` / `quote_documents`：承接已确认的报价和报价单附件。
- `competitor_snapshots` / `review_insights`：承接已确认的竞品与评论主题。
- `audit_logs`：记录 AI 提取、字段确认、拒绝、应用、重试和模型配置变化。

不得建立绕过证据规则和审计的“AI 专用数据通道”。AI 产生的数据只有在来源、字段决策和应用记录完整时，才可以参与确定性门禁。

### 5.6 外部动作分级

| 级别 | 示例 | 默认策略 |
|---|---|---|
| L0 只读 | 解析文件、读取用户已授权的报表 | 可自动，记录来源与访问日志 |
| L1 内部草稿 | RFQ 草稿、Listing 草稿、行动建议、补货提醒 | 可自动，必须标记为未审批草稿 |
| L2 外部写入 | 发送 RFQ、发布/修改 Listing、改价、调广告、补货下单 | 必须人工批准，必须有幂等键和回执 |
| L3 禁止自动 | 付款、退款、赔付、删除数据、绕过平台风控 | AI 不得执行；需要专用人工流程 |

AI 永远不能把“生成草稿”当成“已经执行”。`sent_at`、平台商品 ID、外部回执和发布状态只能由真实外部动作写入。

## 6. 核心数据模型

### 6.1 商品与机会

- `product_cases`：商品机会主表
- `case_evidence`：来源、URL、抓取时间、原始内容、摘要
- `data_sources`：数据源注册表、能力声明、凭证变量名和就绪状态
- `ingestion_runs`：每次导入的文件、入口、行数、结果、告警和完成状态
- `evidence_snapshots`：候选品、供应商、报价等导入原始内容的可追溯快照
- `connector_health_checks`：平台只读授权检查的状态、验证层级、耗时、检查人和非敏感详情
- `cost_models`：假设参数、计算结果、模型版本
- `approvals`：确认门、决策、确认人、意见
- `audit_logs`：所有关键状态与配置变化

### 6.2 供应与样品

- `suppliers`：供应商档案
- `supplier_external_ids`：供应商外部 ID、规范化链接、身份键和首次/最近出现时间
- `rfqs`：询价单
- `quotes`：报价、MOQ、交期、账期、Incoterms
- `quote_documents`：报价来源快照、链接、校验和与导入元数据
- `supplier_selections`：人工定标结果、定标说明、评分快照和成本版本
- `sample_reports`：样品、缺陷、质检结论
- `compliance_documents`：认证和合规文件

### 6.3 内容与上架

- `assets`：图片、视频、文档及其来源和版本
- `asset_lineage`：原图、生成图、局部编辑之间的关系
- `listings`：平台字段 JSON、状态、外部 ID
- `listing_reviews`：内容、合规和平台预检结果

### 6.4 运营与复盘

- `issues`：竞品、库存、广告、差评、Listing 异常
- `experiments`：广告/价格单变量实验
- `actual_results`：实际销量、成本、退款、广告和利润
- `forecast_errors`：预测与实际差异，用于校准模型

### 6.5 AI 自动化任务模型（P2.0 已实现）

P2.0 已新增以下表，并与现有机会、证据和审计表关联：

| 表 | 作用 |
|---|---|
| `ai_tasks` | 任务类型、状态、来源、request hash、target hypothesis、provider、model、attempt、提取摘要、应用实体和错误 |
| `ai_task_artifacts` | 原始文本/文件内容、内容哈希、MIME、文件名、元数据和可选的 `evidence_snapshot_id` |
| `ai_extracted_fields` | 字段名、原值、规范化值、置信度、字段状态、风险级别、校验说明和位置 |
| `ai_field_sources` | 字段与 artifact、原文摘录、字符 locator 和来源类型的关联 |
| `ai_review_actions` | 确认、修改、拒绝、升级审核的人、时间、前后值和说明 |
| `ai_model_calls` | provider、模型、attempt、状态、耗时、输入字符数、脱敏后的响应摘要和错误 |

约束：

- `ai_extracted_fields` 只保存候选值，不替代领域事实。
- 一个字段可以有多个来源；出现不一致时自动进入 `needs_review`。
- `applied_entity_type` 与 `applied_entity_id` 用于追踪最终写入的竞品快照、供应商报价或评论证据。
- 所有表默认 append-only；人工修改通过 `ai_review_actions` 留痕，不覆盖原始 AI 输出。
- 敏感字段（认证、专利、合规声明、品牌授权）不因置信度高而自动通过。
- 一个字段可有多个候选值；冲突候选全部保留，只有人工接受且没有其他阻断项时才允许应用。
- Prompt/schema 的独立版本号和 token/费用字段尚未加入数据模型；当前使用代码内 Schema 与脱敏响应摘要完成首版追溯。

## 7. 技术选型

### 7.1 推荐组合

- Web/API：Next.js + TypeScript。
- 数据库：当前 PGlite；团队化和生产环境迁移到 PostgreSQL。
- Worker：P0 先使用与 Web 同进程的数据库任务执行器，P1 再拆独立 Node/Python Worker。
- 队列：P0 使用数据库任务表和轮询；P1 使用 PostgreSQL `FOR UPDATE SKIP LOCKED`；只有吞吐或延迟确实不足时才引入 Redis + BullMQ/Celery。
- 文件：本地受控目录；团队化后迁移到 MinIO / S3。
- Schema：Zod 或 JSON Schema；模型输出必须在写入暂存表前校验。
- 向量检索：有真实评论/知识库检索需求后再引入 pgvector，不在 P0 先建向量库。
- Agent 原型：Dify（可选），不承载最终业务状态。
- 图片生成/编辑：ComfyUI + 分割/局部重绘模型，先做人审草稿。
- 电商接口：Amazon SP-API、Shopify Admin API、eBay Sell API；1688 / Alibaba 使用官方授权接口。
- 部署：当前使用本机 Node 直接运行和 PGlite；Docker 方案暂缓，后续再评估。P1 迁移 PostgreSQL，P2 再根据团队规模云化。

P0 不引入 Redis、独立微服务和复杂工作流引擎。单用户、低并发阶段，可靠的任务表、幂等键和重试语义比消息中间件更重要。

当前单用户部署只运行一个 Node 应用进程。PGlite 不支持多个应用进程并发写同一数据目录；团队协作阶段迁移 PostgreSQL 后，再扩展应用副本、反向代理、正式备份和恢复流程。

### 7.2 连接器顺序

1. CSV 导入（P1.0 已实现）。
2. AI 证据收件箱的粘贴文本、CSV、JSON、Markdown（P2.0 已实现，内部只读处理并暂存字段）。
3. Keepa ASIN 只读 Adapter（P1.0 已实现，需用户提供 Key 验收）。
4. Amazon SP-API / Shopify 自有店铺只读诊断（P1.1 已实现，需真实凭证验收）。
5. eBay 应用凭证诊断（P1.1 已实现；卖家 OAuth 仍待实现）。
6. AI 供应商助手的 RFQ、缺失信息追问和报价到期提醒内部草稿（P2.1 第一阶段已实现，系统不发送）。
7. 图片/截图/PDF OCR、邮件正文归档和供应商报价单视觉解析（P2.1 第二阶段规划）。
8. AI Listing 操作员的多版本文案、平台字段检查和 payload 草稿（P2.2 规划，发布仍走现有门禁）。
9. 结算、广告、库存和退货报表导入与运营分析（P2.3 规划）。
10. TikTok Shop / 1688 官方授权与诊断（需要应用申请和商家授权）。
11. 真实平台 dry-run、官方写 Adapter、幂等写入与外部回执（P3 规划）。
12. 物流商模板、评论/关键词数据、社媒与趋势数据。
13. 网页自动化兜底（仅在合法合规且无官方 API 时评估）。

不要从爬虫开始。爬虫是最脆弱、最容易封号、最难维护的部分，也不应成为 AI 自动化的第一优先级。

### 7.3 凭证与外部动作边界

- 所有密钥只通过 `.env.local` 或密钥管理系统注入，变量名参考 `.env.example`。
- Keepa 只读；未配置 Key 时不得请求外部接口或生成替代数据。
- CSV 导入只入库，不发送 RFQ、不定标、不发布、不改价、不下单、不付款。
- 平台连接诊断只读；填写全部环境变量也不会自动开放写 Adapter 或发布能力。
- TikTok Shop / 1688 在官方 Adapter 实现前必须保持 `unsupported`，不得伪造连接成功。
- `content_approved` 只代表内部内容门禁通过，不等同于平台 `published`。
- 发布准备必须分开验证正式店铺、官方写 Adapter 和真实平台 dry-run；本地预检不能替代平台 dry-run。
- 当前所有平台均为 `dryRunSupported=false`、`publishingSupported=false`；发布队列确认只进入内部队列，固定记录 `externalActions: none`、`published: false`。
- `approved_for_publish` 不是平台发布结果，不得生成或伪称外部商品 ID、回执或已上架状态。

## 8. 确认门与自动化边界

### 8.1 必审

- 商品立项。
- 供应商定标。
- 商品合规声明、认证、专利和品牌授权结论。
- 进入内部发布队列。
- 新 Listing 发布或重大修改。
- 超过阈值的价格调整。
- 超过预算的广告动作。
- 付款、退款、赔付、首单采购。
- 删除或大幅修改已有 Listing。
- 任何低置信度、来源冲突或无法追溯的 AI 字段。

### 8.2 可以自动处理

- 文件类型识别、OCR、表格解析和字段提取。
- 来源片段定位、内容哈希、去重和缺失字段识别。
- 评论主题聚类、竞品字段归一化和报价字段归一化。
- 确定性成本计算、报价比较、平台长度/必填字段校验。
- Listing 文案草稿、RFQ 草稿、追问草稿和运营行动建议。
- 异常检测、任务排序和提醒生成。
- 生成确认单、索赔材料和可审计报告。

### 8.3 字段级自动接受规则

建议默认阈值如下，实际阈值应通过真实样本校准：

| 情况 | 默认处理 |
|---|---|
| 原文明确、字段在自动接受白名单、无冲突、置信度 ≥ 0.90 | 自动接受为候选事实 |
| 需要单位换算、币种换算、同义字段映射或置信度 0.70～0.90 | `needs_review` |
| 多个来源冲突、来源片段无法定位、置信度 < 0.70 | 必须人工确认 |
| 认证、专利、合规声明、品牌授权、供应商身份最终确认 | 永不因置信度高而自动通过 |
| 模型推断出的销量、利润、风险或“已认证” | 直接阻断，禁止作为事实 |

自动接受不等于让 AI 直接改变商业结论。即使字段自动进入候选表，最终 GO / HOLD / NO-GO、成本模型、供应商评分和发布准备仍由现有确定性代码重新计算。

### 8.4 自动通过的硬条件

一个字段只有同时满足以下条件才可自动接受：

1. 能从 artifact 定位到原文、页码或 OCR block。
2. 字段名在明确的自动接受白名单中。
3. 值通过类型、范围、币种和单位校验。
4. 没有其他来源冲突。
5. 置信度达到配置阈值。
6. 不涉及高风险声明或最终商业承诺。
7. 写入幂等键已经生成。
8. 审计记录包含模型、Prompt、Schema、来源和应用结果。

### 8.5 AI 失败处理

- 模型超时、限流、返回非法 JSON 或 Schema 不匹配：任务失败，保留原始证据，可重试。
- OCR 质量不足：标记待补材料，不生成猜测值。
- 来源不完整：进入人工确认，不进入门禁。
- AI 结果与人工录入冲突：两者都保留，生成冲突卡片，由人决定。
- AI 服务不可用：回退到现有 CSV、人工录入和确定性流程，不阻塞业务。
- 任何 AI 字段应用失败：事务回滚，任务保持未应用状态。

## 9. 验收指标

第一版不追求“无人化”，追求可量化的效率、准确率和可追溯性。以下是上线门槛，不是宣传承诺。

### 9.1 P2.0 AI 证据收件箱（代码验收已通过，真实样本待验收）

自动化测试已覆盖自动接受、低置信度、敏感字段、来源不可定位、跨来源冲突、金额/币种/评分校验、月销量上下限、请求与应用幂等、事务回滚，以及应用后的门禁重算。`npm test`、`npm run typecheck` 和 `npm run build` 通过只代表代码契约成立，不代表真实业务字段准确率已经达标。

以下指标仍需用至少 100 条真实竞品、供应商报价和评论证据完成验收：

- 10 条真实候选品/报价记录从上传到可审核，人工操作时间中位数 < 10 分钟。
- 自动接受字段的来源可追溯率 100%。
- 重复导入不产生重复供应商或报价；幂等验收 100% 通过。
- 重点字段（标题、价格、币种、MOQ、交期、供应商名）精确率 ≥ 98%，召回率 ≥ 90%。
- 低置信度、冲突和无来源字段 100% 进入人工队列。
- 任何 AI 解析失败都不会生成替代事实。
- 审核页面处理 10 个待确认字段的时间中位数 < 5 分钟。

### 9.2 P2.1 AI 供应商助手（内部草稿代码已完成，真实样本待验收）

已由自动化测试覆盖：

- 三类草稿只能从已加入验证的机会生成；追问和到期提醒必须绑定已录入供应商。
- 到期提醒必须先有该供应商的真实报价，提醒日期只能是今天或未来日期。
- 缺失信息问题由确定性代码生成并追加，模型无法删除或替换。
- 模型只返回主题和开场 JSON；Markdown、越权表述、新增数字和过长内容会被拒绝并回退确定性模板。
- 同一事实快照和草稿类型使用 SHA-256 幂等键；重复生成复用已有草稿。
- 草稿状态只有 `draft | reviewed`，审阅幂等，审计固定记录 `externalActions: "none"`、`sent: false`，数据库没有 `sent_at` 或 `sent` 状态。

仍需用真实供应商场景验收：

- RFQ 初稿生成和复核时间中位数 < 10 分钟。
- 至少 20 个真实供应商沟通场景中，草稿无需改写事实字段的比例可量化。
- 缺失问题覆盖率 100%，不得出现模型新增价格、MOQ、交期、认证或有效期。
- 模型不可用或输出非法时，确定性模板仍能生成可用草稿。
- 报价比较和成本回写只由确定性代码完成。
- 当前没有外部发送，因此“发送审批覆盖率”不作为已实现指标；未来增加发送前必须补齐人工批准、幂等和外部回执。

### 9.3 P2.2 AI Listing 操作员

- Listing 初稿人工重写率 < 30%。
- 平台长度、必填字段和禁用词检查覆盖率 100%。
- 未确认的认证、专利、绝对化声明不会进入最终 payload。
- 所有平台版本都绑定商品事实版本、图片资产和预检结果。
- 发布动作仍需现有发布准备门禁和人工确认。

### 9.4 P2.3 AI 运营分析员

- 结算/广告/库存报表导入后，关键字段映射时间 < 10 分钟。
- 预测利润与实际利润差异可按 SKU 追溯。
- 异常行动建议被人工采纳率持续统计，首月目标 ≥ 60%。
- 改价、广告预算、补货和清仓动作 100% 有审批和回滚方案。

### 9.5 安全与效率底线

- 每个选品结论 100% 有来源和数据时间。
- 所有发布动作 100% 有确认和审计记录。
- 不发生无确认的付款、下单、改价、退款或自动发布。
- 每季度用真实样本复测字段准确率，模型或 Prompt 变化后必须重新验收。

### 建议的实际顺序

1. 先用 100 条真实证据验收 P2.0，不要因为 P2.1 代码已落地就跳过字段准确率验收。

3. 运营分析放在已有真实结算、广告和库存报表之后。
4. 多人审核或外部写操作出现前，先完成 P2.4 的最小团队权限与审核分离。
5. 官方写 Adapter 最后接入；AI 流程、审计和字段准确率未达标前不做自动发布。

## 11. 最重要的工程约束

1. 外键、状态机和幂等键优先于 Agent 框架。
2. 所有生成结果有版本、输入快照和来源。
3. 成本计算器必须有单元测试，不能被模型随意重算。
4. 模型输出必须通过 JSON Schema 校验，并经过服务端规则计算字段决策。
5. 外部动作必须幂等，避免重复改价、重复发布、重复退款。
6. 保存原始响应和原始证据，不能只保存模型总结。
7. Prompt、Skill、模型、Schema 和价格规则都要版本化。
8. 先积累真实决策数据，再谈自动优化。
9. AI 先写暂存表，再通过事务写领域表；禁止模型直写核心业务表。
10. 任何自动接受都必须是可解释、可定位、可回滚的。
11. 失败优先于猜测：缺来源、冲突或 Schema 错误时必须进入人工队列。
12. 单个 Skill 可替换，编排状态和审计不可丢。

## 12. P2.0 已落地清单与后续验收

P2.0 文本版已进入代码库。当前可以宣称支持文本、CSV、JSON 和 Markdown 的结构化提取；不可宣称支持图片、截图或 PDF OCR，也不可宣称真实业务字段准确率已经达标。

### 12.1 页面（已落地）

- `/ai-inbox`：从机会验证页进入时预选并锁定当前机会上下文，只显示该机会的任务；直接访问时作为全量队列，可切换目标机会。支持粘贴或上传文本证据、状态/来源筛选和失败重试。
- 当前可提交 TXT、CSV、JSON、Markdown，单文件不超过 300 KB；图片和 PDF 不在支持范围。
- `/ai-inbox/[taskId]`：显示原始证据、候选字段、规范化值、来源摘录、字符位置、置信度、冲突和敏感字段标记。
- 字段级操作已支持 `accept | correct | reject`；不满足自动接受条件的字段进入人工审核。
- 应用区显示写入实体类型与 ID、操作人和时间；页面同时展示门禁结果、审核记录和模型调用记录。
- 页面明确标注没有外部发送、采购、付款、改价或发布按钮。

### 12.2 API（已落地）

- `POST /api/ai-inbox/tasks`：接收文本内容、来源类型、目标机会和提交人，创建任务并按需同步执行提取。
- `GET /api/ai-inbox/tasks`：按状态、来源类型和数量上限查询任务。
- `GET /api/ai-inbox/tasks/[taskId]`：返回任务、artifact、字段候选、来源和审核状态。
- `POST /api/ai-inbox/tasks/[taskId]/retry`：重试失败任务，保留历史 attempt。
- `POST /api/ai-inbox/tasks/[taskId]/fields/[fieldId]`：确认、修正或拒绝字段，保留审核前后值和理由。
- `POST /api/ai-inbox/tasks/[taskId]/apply`：应用前从数据库重新读取并校验，然后在事务中写入业务表。

当前服务端已执行任务状态、字段状态、来源定位、规范化值、冲突和应用幂等校验。由于尚未实现登录与角色权限，接口不能把当前调用者认证为真实团队成员；权限校验属于 P2.4 团队阶段。错误响应已做脱敏，不返回 Secret、Cookie 或 Token。

### 13.3 安全规则（已由测试覆盖）

- 草稿必须绑定已加入验证的机会；供应商相关草稿必须绑定该机会下已录入的供应商。
- 报价到期提醒必须存在该供应商的真实报价，不能凭空生成。
- 提醒日期只接受今天或未来日期，且只代表内部提醒，不代表供应商确认的有效期。
- 模型不能新增输入事实之外的数字；不能输出 Markdown 或“已发送、已联系、已认证、保证、最低价”等越权表述。
- 模型失败、非法 JSON、Schema 不匹配或校验失败时回退确定性模板。
- 重复生成使用事实快照哈希幂等复用；重复审阅幂等；审计固定记录 `externalActions: "none"`、`sent: false`。
